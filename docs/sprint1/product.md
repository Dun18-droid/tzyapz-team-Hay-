## 1. Профіль компанії та контекст продукту

* **Компанія:** ТОВ «СтейНау» (м. Одеса, заснована у 2020 році). Надає платформу прямого онлайн-бронювання для малих готелів та гостьових будинків (до 30 номерів) без посередників у південному регіоні (близько 120 закладів-партнерів).
* **Архітектура та стек:** 
  * Гостьова частина та панель керування: Single Page Application (React).
  * Серверна частина: набір мікросервісів на Java (Spring Boot) для управління номерами, бронюваннями, аналітикою та сповіщеннями.
  * База даних: PostgreSQL.
  * Модуль бізнес-логіки: Java 17, Maven 3.9, JUnit 5 (пакет `ua.kpi.tzyapz.staynow`).
* **Поточна версія (Demo):** Публічний навчальний вебзастосунок *Restful Booker Platform* (https://automationintesting.online). Адмінпанель доступна за адресою `/admin` (обліковий запис: `admin` / `password`).
* **Контекст створення відділу якості:** Відділ QA створено після завершення пікового літнього сезону, під час якого виникла низка інцидентів із подвійним овербукінгом номерів через некоректну синхронізацію перевірки доступності.

## 2. Користувачі та ролі

| Роль | Призначення та права | Доступні функції в продукті |
|---|---|---|
| **Гість** | Клієнт без попередньої реєстрації | Перегляд карток номерів, фільтрація за доступністю у віджеті дат, створення бронювання, надсилання повідомлень через контактну форму |
| **Адміністратор готелю** | Співробітник рецепції з доступом до `/admin` | Створення та редагування кімнат (тип, зручності, ціна), перегляд і обробка заявок гостей, звітність завантаженості |
| **Менеджер** | Керівник закладу | Встановлення базових тарифів, налаштування коефіцієнтів високого/низького сезонів, політики штрафів за скасування та схвалення повернень |
| **Зовнішні учасники** | Служба прибирання, платіжний сервіс | Отримання нарядів на підготовку кімнат після виселення; проведення фінансових транзакцій і повернення коштів |

## 3. Бізнес-процеси для моделювання

Відповідно до нормативу для команди з 3 осіб (Спринт 1, табл. 6), із чотирьох ключових процесів продукту «СтейНау», наведених у Каталозі, для моделювання обрано **Процес 1 («Бронювання номера»)** та **Процес 2 («Заселення і виселення»)**.  
Процеси 3 («Скасування і повернення коштів») та 4 («Обробка повідомлень гостей») у цьому спринті не моделювалися.

## 4. Замовлення на нову функцію: «Сезонні тарифи та політика скасування»

Від керівництва компанії «СтейНау» (дослівно з Каталогу продуктів, п. 6.4):
> *«Готелі просять сезонні ціни і чесні правила скасування. Гість має бачити точну вартість до бронювання, а не дізнаватися про надбавку на рецепції; при скасуванні — одразу знати, скільки повернуть. Правила однакові для всіх готелів платформи, коефіцієнти налаштовує менеджер».*

Шість очікувань замовника (формулювання за Каталогом продуктів):
1. Вартість проживання рахується за ніч із сезонним коефіцієнтом (високий, низький, звичайний сезон).
2. Ночі напередодні вихідних коштують дорожче на фіксований відсоток.
3. За тривале проживання від певної кількості ночей діє знижка на підсумок.
4. Гість бачить розрахунок вартості за ночами до підтвердження бронювання.
5. Політика скасування (без штрафу / частковий / повний) залежить від кількості днів до заїзду і показується до підтвердження.
6. Менеджер налаштовує сезони і коефіцієнти без участі розробників.

*(Примітка: точні значення відсотків і днів визначено у специфікації SN-SRS-01 та зафіксовано в критеріях прийняття відповідних User Stories у беклозі).*
