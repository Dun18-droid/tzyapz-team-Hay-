## Рішення команди (обов'язкові для всіх тест-класів)

1. **Коди помилок — назви з модуля.** Очікуване значення беремо зі змісту правила BL (методичка 4.2), а назва константи — лише ідентифікатор у коді; з назвами SRS 1.1 тести не скомпілюються. Відповідність:

    | Правило BL-10 | SRS 1.1 | У тесті (модуль v1) |
    |---|---|---|
    | Виїзд пізніше заїзду | `INVALID_DATE_ORDER` | `BookingError.CHECK_OUT_NOT_AFTER_CHECK_IN` |
    | Ночей 1..30 | `INVALID_NIGHTS` | `BookingError.NIGHTS_OUT_OF_RANGE` |
    | Заїзд не раніше today | `PAST_CHECK_IN` | `BookingError.CHECK_IN_IN_PAST` |
    | Гостей 1..capacity | `INVALID_GUESTS` | `BookingError.GUESTS_OUT_OF_RANGE` |
    | Email / телефон | `INVALID_EMAIL` / `INVALID_PHONE` | ті самі |

2. **`INVALID_DATE_FORMAT` (null-дати) — не покрито.** Правило додано лише в SRS 1.1 з позначкою «потребує підтвердження замовником»; в оригінальній SRS_04 і в модулі v1 його немає. Дефект на непідтверджену вимогу не оформлюємо; у README і висновку спринта — у переліку непокритого з цією причиною.
3. **Вихідні ночі — п'ятниця і субота** (ніч = дата її початку). Так у SRS 1.1 (BL-30) і в README модуля — розбіжності немає.

## Обов'язкові й додаткові тести

**Обов'язкові — 14** (позначка ★): покривають кожен нетривіальний метод модуля (11 методів) і кожну межу з обох боків — цього досить для нормативу (≥12, ≥3 на особу) і вимоги «всі методи з нетривіальною логікою мають тести». **Додаткові — 7**: пишемо, якщо встигаємо; підвищують шанс знайти більше закладених дефектів (норматив ≥3 з 6).

## Перед тим як оформити «червоний» тест як дефект

1. Перечитати вимогу і перерахувати очікуване вручну (значення в цій матриці вже пораховано — звірити).
2. Перевірити тест: порядок аргументів `assertEquals(expected, actual)`, шкалу `BigDecimal` (`100.00`, а не `100`), той самий метод.
3. Якщо тест правий — звіт BUG-0NN з позначкою `module` (клас, метод, вхід, очікувано/фактично, ID вимоги, ID тесту); ID звіту — у коментарі тесту і в колонці «Статус». Тест лишається червоним.
